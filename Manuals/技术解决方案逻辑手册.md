### 2. “三位一体”的更新监测逻辑 (Monitoring)

不要等插件坏了才去修，要建立主动感知的“情报网”：

- **社区感知**：利用 **n8n** 监控 Obsidian 官方论坛和 GitHub 的 Release 页面。
    
- **AI 审计**：每两周将你的插件列表发给我（或通过 Cursor 索引），我会帮你去检索：“最近这些插件有没有重大的架构升级或更优的替代者？”
    
- **实战验证**：每次更新插件后，必须运行一次你的 Skill (P1) 脚本，确保“底层代码”和“上层插件”没有断层。

### 🛠️ 其它步骤的维护原则 (P1-P3)

除了插件，针对我们之前定的 **Skill、Dify、CLI** 步骤，也需要一套硬性原则来指导：

#### P1: Skill 开发原则 —— “原子化与无状态”

- **原子化**：一个 Skill 只干一件事。如果一个脚本既要抓取网页又要保存到网盘，拆开它。
    
- **无状态 (Stateless)**：Skill 运行不依赖于复杂的本地路径配置。使用环境变量或 JSON 配置文件。这样你的 Skill 丢给 Dify 能跑，丢给 CLI 也能跑。
    

#### P2: Dify / n8n 部署原则 —— “逻辑可视化与解耦”

- **先连线，后调优**：不要在 Dify 里一上来就写复杂的 Python 节点。先用原生节点把逻辑跑通。
    
- **解耦**：Dify 只负责“思考逻辑”，n8n 只负责“数据搬运”。如果你的 n8n 里的连线像蜘蛛网一样乱，说明你的 Skill (P1) 还没封装好。
    

#### P3: CLI 交付原则 —— “统帅友好型界面”

- **自解释性**：所有 CLI 必须包含 `--help`。
    
- **日志留痕**：所有的 CLI 操作必须自动向 `小憶`（日志 Agent）汇报。即使是在终端跑的一行命令，也要在 Obsidian 的日记里留下“执行成功”的痕迹。

### 4. 技术应用决策流 (Decision Tree)

1. **需求产生**：例如“我想自动整理孩子假期的 AI 学习记录”。
2. **情报检索 (小报/P0)**：搜索是否有现成的 Obsidian 学习统计插件？
3. **能力封装 (小酷/P1)**：若插件不给力，写个 Python Skill 提取特定格式的笔记内容。
4. **流程串联 (n8n/P2)**：用 n8n 定时扫描文件夹，触发 P1 脚本。
5. **资产化 (小黑)**：将处理后的结果转为结构化 JSON，存入 `000_Cabinet_System`。
6. **汇报总结 (小憶)**：提醒 Kenny 审核，并记录到当天的简报中。
