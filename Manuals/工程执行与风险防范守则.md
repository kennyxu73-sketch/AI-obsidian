# 工程执行与风险防范守则 v2.0 (长期系统化版)

  

执行目标：确保单体或批量 .md 文件及其衍生 YAML 在长期系统运行中安全、无损、可审计地处理，同时支持 embedding 流程和自动化升级。

核心原则：不可逆操作必须抽样验证，所有自动化必须有“熔断/挂起”机制，所有操作留痕可回溯。

---

## 一、物理放置与路径规则 (File Topology)

1. 影子存放 (Shadow Storage)
    
    - 派生文件不得平铺在主文件夹根目录。
        
    - 每个 note.md 所在目录下创建 .cabinet 或在全局根目录创建 .metadata 存放 YAML 文件。
        
    - 脚本必须支持 RELATIVE_PATH，移动文件夹不破坏双链。
        
    
2. 命名冲突防范
    
    - 主文件 Note_A.md 的派生文件必须命名为 Note_A.card.yaml / Note_A.audit.yaml。
        
    - 遇同名文件脚本必须挂起并报错，禁止自动覆盖。
        
    
3. 版本与规范同步
    
    - 派生 YAML 的 yaml_spec_version 与守则版本保持一致。
        
    - 执行时记录守则版本号到日志。
        
    

---

## 二、链接稳定性规则 (Link Integrity)

1. ID 唯一性校验
    
    - 在裂变前全局扫描 file_id，重复 ID 必须终止执行。
        
    
2. 双链语法规范
    
    - note.md Frontmatter 中 card: "[[path/to/note.card.yaml]]"、audit: "[[path/to/note.audit.yaml]]"必须使用绝对路径或标准 Wikilinks。
        
    - UI 层点击跳转必须可用。
        
    
3. 血缘守恒
    
    - 所有派生 YAML 与主文件 file_id 一致。
        
    - 严格维护 parent_doc 字段（可选），防止孤儿文件。
        
    

---

## 三、鲁棒性与异常防范 (Robustness & Fault Tolerance)

1. 原子化写入 (Atomic Write)
    
    - 严禁直接覆盖原文件，必须生成 .tmp，验证成功后替换。
        
    
2. 幂等性 (Idempotency)
    
    - 脚本多次运行结果一致。
        
    - 如果 yaml_spec_version: 2.0，进入增量同步模式，仅更新变动字段。
        
    
3. 大文件流式读取
    
    - 超大型资产必须使用 Streaming 流式读取，禁止一次性读入内存，防止 OOM。
        
    
4. 批量并行安全
    
    - 增加文件级锁机制，防止多线程或批处理同时操作同一文件。
        
    
5. 回滚机制
    
    - 保留原版 .md、.card.yaml 快照，可通过 hash 或 checksum 验证完整性。
        
    
6. 操作审计日志
    
    - 记录执行人/Agent、时间、操作摘要、hash 值，用于回溯与合规。
        
    

---

## 四、语义清洗与 Embedding 预处理 (Sanitization & Embedding Prep)

1. 脱敏与清洗
    
    - 移除隐私标记、双链 [[]]、图片嵌入 ![[...]]。
        
    - 可通过配置文件定义正则规则，方便后续更新。
        
    
2. 摘要生成保底机制
    
    - 若 AI 生成 summary 失败，填充 [Pending AI Summary]，记录日志。
        
    - 避免生成空 YAML 导致 embedding 输入失效。
        
    
3. Embedding 流程隔离
    
    - note.audit.yaml 禁止进入向量化。
        
    - Embedding 输入仅为 note.md 正文 + note.card.yaml.summary。
        
    

---

## 五、异常与熔断机制 (Error & Circuit Breaker)

1. 异常自动挂起
    
    - 生成 .halt 文件，人工介入处理后再继续。
        
    - 包括重复 ID、无法写入、summary 超时等。
        
    
2. 通知机制
    
    - 异常可触发邮件/企业 IM/Slack 通知负责人或 Kenny。
        
    
3. 增量同步模式
    
    - 当检测到文件已升级到 v2.0，脚本仅更新变动字段，避免全量重写风险。

## 六、交付前强制说明项 (Pre-delivery Report)

  

在 CLI 工具或批处理结束后，必须向 Kenny 或负责人提交：

1. 资产统计：处理总数、成功数、跳过数（无 ID 或重复）。
    
2. 影子路径：所有派生 YAML 的实际物理存放位置。
    
3. 异常清单：无法生成 summary 或生成失败的文件 ID 及原因。
    
4. 血缘完整性声明：所有 file_id 在三位一体文件中一致。
    
5. 版本与执行记录：守则版本、执行人/Agent、hash 验证。

# 七、编码后/执行前：工作说明规范 (Pre-execution Manifest)

**指令场景**：当 Cursor 完成代码编写或准备执行大规模批处理前，必须先输出此说明，由 Kenny 审核。

### 1. 物理拓扑映射图 (Topology Mapping)

Agent 必须明确说明其选定的影子路径逻辑：

- **存放位置**：是选择“目录内隐藏文件夹（`.cabinet/`）”还是“全局元数据库（`.metadata/`）”？
    
- **路径算法**：如果 `note.md` 移动了位置，脚本如何重新链接对应的 `.yaml`？（必须说明是否采用了基于 `file_id` 的相对路径计算方案）。
    

### 2. 内存与并发压力对策 (Concurrency & Memory Strategy)

针对 4GB 资产的工程防范：

- **读取模式**：是否使用了 `Generator/Streaming` 模式？（严禁一次性将全量内容 Load 进内存）。
    
- **速率限制 (Rate Limiting)**：在调用 Ollama 生成 `card.summary` 时，如何防止请求过快导致 3090 显存溢出？（必须交代线程池数量或重试间隔）。
    

### 3. 正则清洗逻辑预览 (Sanitization Preview)

在构造 Embedding 输入前，Agent 需要展示其清洗逻辑：

- **示例输出**：提供一个“清洗前”和“清洗后”的文本对比示例。
    
- **脱敏范围**：是否已包含对个人隐私标记（如手机号、特定地址格式）的过滤规则。
    

### 4. 幂等性与“防灾”机制 (Idempotency & Safety)

- **增量判断标准**：Agent 如何定义一个文件“已升级”？（是通过 `yaml_spec_version: 2.0` 标识，还是对比文件的 MD5 值？）。
    
- **中断恢复**：如果执行到第 500 个文件时崩溃，重启脚本后是否会从第 501 个开始，还是会重新扫描？
    

### 5. 环境依赖清单 (Environment Audit)

- **工具链**：使用了哪些 Python 库（如 `PyYAML`, `regex`, `ollama-python`）？
    
- **版本要求**：对本地 Ollama 运行的模型（如 `qwen2.5:7b`）是否有特定版本要求？

## 八、安全与权限 (Security & Permissions)

1. 临时 .tmp 文件写入权限控制，防止非授权访问。
    
2. 完成写入后，派生 YAML 访问权限可设置为只读或受控组。
    
3. 可选加密敏感内容，确保 embedding 流程前数据安全。

## 九、长期系统运行与维护 (Long-term Operations)

1. 守则升级增量原则
    
    - 新守则必须向下兼容，原始标签和核心字段不得丢失。
        
    
2. 滚动审计
    
    - note.audit.yaml 包含历史日志，记录每次升级、增量修改和 summary 修正。
        
    
3. 批量维护支持
    
    - 支持目录或项目级批量执行，所有规则在批处理环境下保持一致。
        
    
4. 可配置化
    
    - 隐私脱敏、双链清洗、占位符规则、异常处理可通过配置文件统一管理，便于长期维护
